# Client portal interaction prototype

This is a throwaway design capture for monorepo#3934, kept on codex/client-portal-prototype-3934, outside production main. Open index.html locally; it needs no packages, server or network connection.

## Question answered

Can the client and operator follow approval, current-quote acceptance, credited-funds confirmation and oldest-eligible-first work release without interrupting active work?

A new inquiry starts unapproved; accepting a quote cannot release work. The operator simulates matching credited funds, and only the oldest eligible request can start when no request is active. Requoting invalidates acceptance and funds while preserving submission order.

## Confirmed first-release choices

- Public application source; private customer-work inbox.
- Invitation-only initially, with Google and Microsoft through one federated sign-in service.
- Invoice and operator-confirmed bank transfer.

Hosting and operating-budget approval remain unanswered. These choices are shown in the prototype, not connected services.
The planned portal will use a single standards-based OIDC integration with a federated identity service
such as Dex. Google/Microsoft connectors belong to that service, not to bespoke portal
integrations. Reuse the existing platform federation where appropriate after reviewed setup;
the portal still enforces its invitations, customer access and session lifecycle.

## What this is not

All seed data is fictional and state exists only in memory. Role switching is not authentication. Quote acceptance is not a contract, and funds confirmation is simulated. No customer records, credentials, payments, GitHub jobs, agent execution or production routing are present. No bank-transfer irreversibility is promised. The real application needs server-enforced identity, access isolation, durable atomic queue, private terms and independently verified credited funds.
