# ADR 0009 — Two-way SMS as the direct maintainer channel, replacing the Slack DM

- **Status:** Proposed — the maintainer accepts by merging
- **Date:** 2026-10-17
- **Deciders:** Maintainer (request of 2026-10-17); Agentic Engineer
- **Issue:** [#4275](https://github.com/devantler-tech/monorepo/issues/4275) (spike)

> 🤖 Generated by the Agentic Engineer (interactive Claude Code session)

## Context

The direct maintainer channel is a DM to the maintainer's own Slack user: the last resort for a
genuine blocker. Platform alerts go to Slack too: Flux, Alertmanager, Coroot and a few scheduled
checks all post through one shared Slack webhook. The DM has one measured weakness:
Slack never pushes a user's own message, so an ask waits until he happens to open Slack, and on
2026-10-06 ten answers had sat unread in reply threads for up to three weeks
([#3888](https://github.com/devantler-tech/monorepo/issues/3888)). The maintainer has asked for
**SMS to his mobile phone, with replies**, as the replacement.

The channel must stay **reserved for things that actually require him**. Agents resolve what they
can on their own and never send status. Three properties make SMS harder than Slack, and they shape
every rule below:

- **A sender number is not an identity.** Inbound caller IDs can be spoofed, so "the reply came from
  his number" proves nothing on its own.
- **SMS is not end-to-end encrypted.** The provider and the mobile networks can read every message.
- **His mobile number is personal data.** It must never appear in a repository, an issue or a log.

## Decision

Use **Twilio's EU region (Ireland) with a rented Danish mobile number** as the SMS provider. One
GitHub Actions workflow sends every message and reads replies by polling Twilio's authenticated
message list. **No public endpoint anywhere receives SMS.**

Twilio wins over the Danish provider GatewayAPI on one point. GatewayAPI delivers replies only by
webhook, so it would need a new public, unauthenticated route into the cluster and a new service
behind it. Twilio lets the sender fetch replies through the same authenticated API it sends with, so
there is no provider callback for anyone to forge. The monthly costs are almost the same. The trade
is the company: Twilio is a US company, and its EU region keeps message bodies and recipient numbers
in Ireland, with documented exceptions (see *Privacy and data residency*).

Two facts must be confirmed when the account is opened, before anything is built:

- that a Danish mobile number with SMS can be rented;
- that the number works in the EU region.

If either fails, the fallback is **GatewayAPI's EU setup with a Danish virtual number**. The reply
follow-up then becomes a receiver in the cluster that checks GatewayAPI's webhook signature, with its
secrets held in OpenBao. Everything else in this record stays the same.

### How the pieces fit

**One reviewed GitHub Actions workflow in this repository is the only thing that sends an SMS or
reads a reply.** It runs on GitHub's infrastructure, outside both things an alert is usually about:
the agent host on the home network and the production cluster at the hosting provider. A sender
inside either would go quiet in exactly the outage the maintainer most needs to hear about. It also
needs no new service, no new image and no new public route into the cluster.

- **Secrets:** the provider credential, the maintainer's number and the reply-code key are secrets of
  a protected environment that only the default branch can use. No agent, host or cluster component
  holds them.
- **Agent asks:** an agent records the ask on its issue first, then dispatches the workflow with a
  pointer to that record and nothing else. The workflow re-reads the record itself, accepts it only
  from the exact `devantler` login with the 🤖 disclosure line on a `devantler-tech` issue, builds
  the message from a fixed template, applies the limits below and records the delivery on the issue.
  An injected agent can therefore ask for an SMS only about a real, public, disclosed ask, in the
  template's words, within the ceiling.
- **Platform reachability:** the same workflow probes the public sites and the cluster's public entry
  point on a schedule, from GitHub's network rather than ours.
- **Platform incidents:** the agents already read live production health every run. A critical
  incident they cannot resolve becomes an ordinary agent ask, so incidents need no direct Coroot-to-SMS
  integration, and an agent always tries first.
- **Replies:** on a schedule (every ten minutes by default), the workflow reads new inbound messages
  to the Danish number through Twilio's authenticated message list. It checks each one as described
  below, then deletes it from Twilio. A reply therefore takes up to one polling interval, plus any
  delay in GitHub's scheduler, to arrive. That is fine for decisions, which today wait hours.
- **Recording replies:** the workflow posts each verified reply through a dedicated GitHub App that
  nothing else uses, so a reply record from that exact identity can only have come from this
  workflow. The App needs only permission to write issue comments.

### What may trigger an SMS

An SMS is sent only when **the maintainer must act and no agent can**. The bar is the one the Slack
DM has today: genuinely blocked after trying to resolve it.

| Source | Qualifies | Stays in dashboards and issues |
|---|---|---|
| **Agent asks** | An `authority` blocker that names an act only he can perform — a payment, a legal identity or signature, a credential no lane holds, or a refusal by a lane's own permission layer, filed once per refusal class | A decision about our own work, an act a lane's own access can perform, a review or merge, anything already approved |
| **Agent outages** | The sibling-lane watch's `ESCALATE` verdict: a lane not producing for three hourly slots, cause class other than `quota/billing` | `WATCHING`, `KNOWN-RESET`, a degraded single entry |
| **Agent host** | The disk or worktree escalations that already page him, once the reclaim has failed | Anything the reclaim fixed |
| **Platform, reachability** | Public sites or the production cluster unreachable from the public internet for two consecutive checks | A single failed probe |
| **Platform, incidents** | A critical Coroot incident on a user-facing service that is still open after one full agent cycle and needs a human act (power, hardware, the network, a maintainer-only credential) | Warnings, non-critical SLO burn, deployments, an incident an agent is fixing |
| **Security** | A confirmed leak of a credential only he can rotate, or a confirmed active exploit | Scanner findings, CVEs, posture deltas — those become sanitized issues |
| **Money** | Never by SMS. A financial decision goes only to the private channel the spend contract names | — |

Deduplication and limits:

- **One SMS per blocker.** The ask is recorded on its issue's blocker line as `| asked sms <date>`,
  exactly as `| asked slack <date>` is today, and is renewed only when the blocker check reports it
  `STALE-ASK` (14 days). An alert is keyed on its incident; a reopening within six hours sends
  nothing new.
- **No status, ever.** No "resolved", no "found nothing", no summaries, no savings. There are three
  exceptions, each bounded: the receipt for a recorded reply and at most one "not understood" a
  day, both described below, and the waiting-asks notice under the ceiling.
- **A hard ceiling of three asks a day and ten a week.** Over the ceiling, asks wait. The next
  morning carries one notice that names how many are waiting and links the board filter. The notice
  counts as one of that day's three.
- **Urgent alerts do not queue behind asks.** The reachability and security rows have their own
  limit instead: one SMS per incident, and at most three such alerts a day. Past that limit, the
  third alert of the day says that more are open and that the details are in Coroot and the issues.
  An urgent alert is never held back for an ask.
- **Quiet hours from 22:00 to 07:00 Danish time.** Only the reachability and security rows send at
  night. These hours are a default he can change.

### How a reply becomes a maintainer instruction

The reply path is the security-critical part, so it is built to fail closed at every step.

1. **Each ask carries a short reply code and numbered options.** Example (illustrative only):
   `devantler-tech AI: decision needed on ksail#123. Reply "K7Q2X 1" to approve, "K7Q2X 2" to
   decline. Details: <link>`. The code is five characters from a 32-letter alphabet without
   look-alike characters (about 33 million values).
2. **The code is derived, not stored.** It is an HMAC of the ask's public identifier (the issue and
   the ask comment) and its send time, keyed by a secret that only the sender holds. Nothing that
   would let someone compute a valid code is ever written to a public place.
3. **A reply is accepted only when every check passes:** it was read through the provider's
   authenticated API (or, with the fallback provider, its webhook signature verified);
   the sender matches the maintainer's number (compared against the secret, necessary but never
   sufficient); the reply is exactly `<code> <option>`, ignoring case and spaces; the code matches an
   open ask; the option is one the ask offered; the ask is less than seven days old; and no earlier
   reply to that ask was recorded. After three wrong codes in a day, SMS replies stop being accepted
   until the next day. With at most ten asks open, a forger who already knows both numbers and can
   spoof the sender has roughly a one-in-a-million chance a day of hitting a valid code. Locking
   replies out costs the maintainer nothing he cannot do on GitHub.
4. **Anything else does nothing.** Free text, a wrong or expired code, an unknown sender or an
   unreadable delivery is discarded without action and without being posted anywhere public, since
   it may be attacker-written. It is counted, and the maintainer gets at most one "not understood —
   answer on GitHub" SMS a day.
5. **A verified reply is recorded before anything acts on it.** The sender posts a structured comment
   on the issue the ask names: which ask, which option, and that the checks passed — never the raw
   message. That record, from the sender's own dedicated identity, is the only form in which an SMS
   reply reaches an agent. It carries the same limits as a reply in the Slack thread: it answers that
   ask only, and it cannot loosen a guardrail.
6. **Every recorded reply gets a one-line receipt by SMS.** The receipt exists to catch forgery:
   someone who intercepted an ask and answered first is exposed the moment the maintainer receives a
   receipt for an answer he never sent. He then corrects it on GitHub, where his comment outranks the
   SMS record.
7. **The options themselves are safe to forge.** A spoofed and correctly guessed reply can only pick
   one of the options the agent itself offered. So an ask never offers an option that moves money,
   hands over or rotates a credential, deletes data, or widens a permission; those asks say
   "decide on GitHub" and offer no SMS option.
8. **Never a credential by SMS.** No ask requests one, every ask's link points to GitHub for anything
   beyond picking an option, and an inbound message is never parsed for anything except the reply
   format.

### What an SMS may contain

- **Nothing that is not already on the linked GitHub artifact.** An ask carries a short summary, the
  reply code and options, and one link. The only links allowed are to `github.com/devantler-tech`.
  An ask on a private repository carries only the options and the link, never a summary.
- **Never** secrets, credential names or scopes, hostnames, IP addresses, topology, weakness
  details, financial figures, or personal data about anyone.
- **Platform alerts use a fixed vocabulary** — for example "public sites unreachable" or "critical
  incident needs you" — and name Coroot rather than link to it, because no hostname goes into an
  SMS.
- **Plain GSM-7 text, at most 160 characters,** so each message is one segment. An emoji would switch
  the whole message to a 70-character encoding, so the disclosure is a short plain-text prefix,
  `devantler-tech AI:`, instead of the 🤖 line GitHub artifacts carry.

### Privacy and data residency

- **The number lives only in a secret store:** the sender's GitHub environment secret, or OpenBao if
  the fallback's receiver is ever built. It is passed to the provider with each request and never
  saved there as a contact or a group.
- **Logs never show a number, a reply code or a message body.** Workflow logs on a public repository
  are public, and a logged code would let anyone forge a reply. Every value read from an inbound
  message is masked before it is handled.
- **Residency.** Twilio's EU region processes and stores message bodies and the recipient's number in
  Ireland. Its documented exceptions are the mobile networks themselves, redundant routing that may
  cross regions, and support staff outside the EU working under data-transfer safeguards. The region
  uses its own credentials, so the integration uses those from the start. The fallback,
  GatewayAPI's EU setup, runs at Hetzner in Germany with routing inside the EU, a data processing
  agreement and yearly ISAE 3000 and 3402 assurance reports.
- **What the provider holds.** Outbound messages carry nothing the linked GitHub artifact does not.
  The personal data at stake is his number, his replies, and any inbound message from anyone to the
  Danish number. That last group can be free text holding anything at all. The sender never
  interprets it and never copies it anywhere. Every inbound message, verified or not, is deleted from
  the provider once processed, and outbound bodies are not retained where the provider's API allows
  it. Deletion is not instant erasure: Twilio states that message bodies may stay in its database
  backups for up to 30 days after deletion.

## Cost

List prices seen on 2026-10-17, excluding VAT. Twilio notes that carrier fees may be added on top
of its per-message rate and publishes no amount for Denmark, so its figures below are a floor, not
an all-in price. GitHub Actions minutes are free on this public repository, so polling adds no
cost.

| Item | Twilio, EU region (chosen) | GatewayAPI, EU setup (fallback) |
|---|---|---|
| Danish number | USD 15 a month | DKK 105 a month, plus DKK 100 once |
| SMS sent to a Danish mobile | USD 0.0592 each | DKK 0.299 each |
| SMS received | USD 0.0075 each | Not published |
| **Expected month** (about 20 sent, 10 received) | **about USD 16.3 (about DKK 110)** | about DKK 111, plus received messages |
| Month at the ask ceiling (about 90 sent, 45 received) | about USD 21 | about DKK 132, plus received messages |

The expected month assumes the trigger list above: a few asks, their receipts and the rare alert.
Both limits bound the worst case, so a runaway agent cannot run up the bill: each urgent alert
adds about USD 0.06, and there are at most three a day.

## Options considered

| Option | What it offers | Why it was not chosen |
|---|---|---|
| **Twilio, EU region** | Danish long numbers with two-way SMS; replies readable through the authenticated API, so no endpoint is needed; resource-scoped API keys; a published 99.95 % API service level | **Chosen.** Two facts to confirm when the account is opened (see *Decision*) |
| **GatewayAPI** (Danish) | EU hosting, a data processing agreement and assurance reports; Danish virtual numbers; HMAC-SHA-256 signed webhooks | **Fallback.** Replies arrive only by webhook, so it needs a public, unauthenticated route into the cluster and a new receiver service |
| **CPSMS** (Danish) | Low prices, replies to a dedicated number or a keyword | The reply callback is an unsigned GET request with the message text in the query string, and data location and the dedicated number's price are not published |
| **46elks** (Swedish) | Servers in Sweden, simple API | Danish numbers and receiving are priced "call us", and callbacks are authenticated by source address only, with no signature |
| **Vonage** | Signed callbacks are possible | Signing is off by default and enabled only by support, EU isolation for SMS is a closed beta, a Danish number is on request with company paperwork, and prices are not public |
| **An Android phone as gateway** | A real Danish SIM for about DKK 40–80 a month plus a spare phone; signed webhooks | A physical single point of failure on the home network and power, and Android's background limits delay or stop it. In cloud mode messages pass through the vendor's relay and Firebase; in local mode the phone must be reachable from the internet to send. Kept as the documented last fallback |
| **A USB LTE modem** (Gammu or smstools) | Full local control | The same home single point of failure. Gammu documents a preventive reset to reduce modem hangs, so it needs a power-cycle watchdog as well as a home machine to run on |
| **One relay service in the cluster** | Native Coroot webhooks, low latency | It would share the cluster's failure domain, so it could not report the cluster down, and it adds a service, an image and a public route |
| **Coroot calling the provider directly** | No new component for alerts | The maintainer's number would have to sit in Coroot's configuration, nothing would apply the limits, and it skips the agents' attempt to resolve an incident first |
| **Keep the Slack DM** | Already works | It never pushes his own messages, which is the measured problem this record exists to solve |
| **The runtime's push notification** | Reaches his phone | It failed twice in unattended runs (2026-09-08, 2026-09-13) and cannot carry a reply |

## Consequences

- The maintainer gets an alert that actually reaches his phone, and answers a decision with a
  two-word reply instead of opening Slack.
- Every SMS has a cost, so the ceiling and the trigger list are part of the cost control, not only of
  the attention budget.
- A new outbound destination and a new control surface enter the contract. Both are deliberately
  narrow, and both land through the follow-ups below rather than through this record.
- Slack remains in place until the SMS path has been proven end to end; the channel switch and the
  Slack retirement are separate, later steps.
- One gap remains: when both agent lanes are down at once, neither can page. The sender's own
  schedule could close it by checking recent lane activity on GitHub; that is left out of the first
  slice on purpose.

## Steps only the maintainer can take

Agents never create accounts, sign agreements, enter credentials or move money. These steps are his:

1. **Open the provider account** in the business's name, accept its terms and data processing
   agreement, and add a payment method. For Twilio: open it in the EU region (Ireland), rent a
   Danish mobile number, confirm that it supports SMS and works in that region, and create an API
   key scoped to messages only. Twilio documents no paperwork for Danish mobile numbers, only for
   local ones. If either check fails, stop and say which, and the GatewayAPI fallback applies.
2. **Create the dedicated GitHub App** for reply records, with permission to write issue comments
   only, and install it on the organisation.
3. **Enter the secret values** in the protected environment that the sender follow-up creates: the
   provider credential, his mobile number, the reply-code key (any 32 random bytes) and the App's
   private key. Agents prepare the environment and the exact list; the values never pass through an
   agent.
4. **Approve the channel switch** by merging that follow-up, and apply the prepared change to the
   machine-local scheduler pointers that name the Slack write action.
5. **Optionally adjust the defaults** — the daily and weekly ceilings and the quiet hours — at any
   time by editing this record's successor or the sender's configuration.
