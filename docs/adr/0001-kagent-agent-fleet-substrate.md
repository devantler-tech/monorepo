# ADR 0001 — kagent as the Agentic Engineer fleet substrate

- **Status:** Proposed — adoption requires the live-cluster and cost/quality gates below
- **Date:** 2026-07-07
- **Deciders:** devantler-tech maintainers
- **Issue:** [#2075](https://github.com/devantler-tech/monorepo/issues/2075), part of
  [#2074](https://github.com/devantler-tech/monorepo/issues/2074)

> 🤖 Generated by the Agentic Engineer

## Context

The portfolio needs a Kubernetes-native substrate for high-volume mechanical agent work such as
CI-log triage, dependency updates, and documentation synchronization. Expensive provider runtimes
remain responsible for work that needs broad context and engineering judgement.

[kagent](https://kagent.dev) is the proposed substrate. It supplies declarative agents, model
selection, MCP tool registration, agent-to-agent delegation, sandboxed execution, and standard
telemetry. The proposal stays gated because kagent is pre-1.0, its CRDs are alpha, and the portfolio
does not yet have live cost/quality evidence for the intended model tiers.

## Current architecture

### Runtime

kagent consists of a Go controller, an agent engine/application server, a UI, and a CLI. Its core
`kagent.dev/v1alpha2` resources are:

- `Agent` for prompts, tools, sub-agents, and model references;
- `ModelConfig` and `ModelProviderConfig` for model access;
- `ToolServer` and `RemoteMCPServer` for tool access;
- `AgentHarness` and `Memory` for runtime behavior and state.

The Agent Substrate adds `WorkerPool`, `ActorTemplate`, and sandboxed actors. A worker serves
sequential short-lived sessions, while actor state can be snapshotted to object storage. This is the
selected runtime shape because it gives mechanical workloads a dense execution pool and a gVisor
isolation boundary.

### Models

Each `Agent` selects a model through `ModelConfig`.

- In-cluster Ollama serves the highest-volume, lowest-stakes tasks with infrastructure cost instead
  of per-token cost.
- Claude Haiku serves mechanical tasks that need a stronger hosted model.
- The provider runtime's frontier model remains the orchestrator for judgement-heavy work.

Every task class requires measured quality and cost evidence before it is assigned to a cheaper tier.

### Cluster fit and delivery

kagent has no service-mesh dependency and fits the portfolio's Cilium clusters. The `istio-agent` is
an optional operational agent, not a runtime requirement.

The deployment uses Flux with pinned OCI Helm chart versions:

1. `OCIRepository` and `HelmRelease` for `kagent-crds`, with CRD replacement enabled;
2. `OCIRepository` and `HelmRelease` for kagent;
3. an external PostgreSQL service;
4. agent, model, and tool resources stored in Git and reconciled by Flux.

Pinned chart versions are mandatory because the API is pre-1.0 and the CRDs are
`kagent.dev/v1alpha2`.

### Tools and agent topology

MCP servers are registered as `ToolServer` resources and granted to individual agents explicitly.
The fleet uses agent-to-agent delegation with separate survey, product-action, and report
responsibilities. Each agent receives only the tools and credentials required for its role.

### Observability

OpenTelemetry traces are the primary run-level signal. The evaluated v0.9.11 charts also provide
opt-in `ServiceMonitor` resources for `kagent-tools` and the bundled OAuth proxy. Those resources
require the Prometheus Operator CRDs and remain disabled unless the target cluster has a compatible
metrics consumer.

## Decision

kagent is the conditional choice for the portfolio's mechanical agent fleet. Adoption is authorized
only after the two open gates under *Adoption gates* pass.

The accepted deployment shape is:

- Agent Substrate with a small, pinned worker pool and gVisor actors;
- model selection per task class through reviewed `ModelConfig` resources;
- Flux-managed charts and CRs;
- external PostgreSQL;
- A2A delegation between narrowly-scoped agents;
- MCP tools granted per agent;
- OpenTelemetry traces and compatible metrics collection;
- exact chart and CRD version pins.

The existing provider runtimes remain the authoritative writers and orchestrators. kagent workers do
not receive independent merge authority, a new branch namespace, or credentials broader than the
consumer contract permits.

## Security constraints

The model does not enforce the portfolio trust boundary. Tool capabilities, credentials, Kubernetes
RBAC, namespace isolation, and sandboxing enforce it.

The default `kagent-tools` permissions are not acceptable: the evaluated chart grants wildcard
cluster resources, non-resource URLs, and verbs. Any portfolio deployment must set all of:

- `rbac.readOnly: true`;
- the matching application-level `--read-only` mode;
- an explicit namespace allow-list;
- `rbac.allowSecrets: false`, unless a separately reviewed role grants named secret access.

The Agent Substrate roles remain read-only and resource-scoped. Secret access uses namespace-scoped
roles with `resourceNames`. No worker may push to `main`, merge external work, bypass the draft/review
contract, or execute untrusted repository code.

## Adoption gates

1. **Live Cilium boot:** install the pinned charts through Flux on a disposable Cilium cluster,
   observe healthy controllers and runtime components, and complete one prompt → tool call → result
   path without Istio. Tracked by
   [#2076](https://github.com/devantler-tech/monorepo/issues/2076).
2. **Cost/quality benchmark:** compare at least two cheap model tiers across at least two
   representative mechanical tasks. Record cost per task, outcome quality, and the task classes each
   tier may handle. Tracked by
   [#2076](https://github.com/devantler-tech/monorepo/issues/2076).

The evaluated v0.9.11 chart shape already establishes these closed constraints:

- no admission webhook is required;
- no dedicated `Team` CRD exists;
- the default tools RBAC requires the hardening above;
- the Agent Substrate supplies the selected least-privilege runtime shape;
- native metrics integration is opt-in.

## Consequences

- Mechanical work gains a Kubernetes-native, GitOps-reconciled execution pool with explicit
  capabilities and standard telemetry.
- The portfolio can select model cost and quality per task without moving judgement-heavy work away
  from the provider runtime.
- Pre-1.0 APIs and chart changes require pinned versions, reviewed upgrades, and contract tests.
- The fleet adds PostgreSQL, worker-pool capacity, model-serving capacity, and agent-policy
  maintenance.
- Adoption remains blocked until live cluster behavior and cost/quality are observed.
