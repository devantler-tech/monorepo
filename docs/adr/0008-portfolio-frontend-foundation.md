# ADR 0008: Portfolio frontend foundation

Status: Proposed — Svelte migration direction selected; comparative spike remains open

Date: 2026-10-15

## Context

The business website now combines a bilingual public portfolio, Journal and a developing
private customer/operator application. Its Astro content baseline is not evidence that
Astro is unsuitable, nor that one replacement will be faster for every workload. The
maintainer has requested a common, quality-led frontend direction before completing the
portal, without using stars, downloads or popularity as a quality measure.

The frozen comparison plan is [monorepo #4019](https://github.com/devantler-tech/monorepo/issues/4019#issuecomment-6201670881).
Its security, correctness, privacy, accessibility and recovery floors cannot be traded for
a performance score. The linked [adoption epic](https://github.com/devantler-tech/monorepo/issues/4222)
tracks implementation separately from the investigation.

## Decision and its present limits

Select **Svelte 5, SvelteKit 3 and TypeScript** as the best-supported migration direction
for new or materially changed general-purpose portfolio web interfaces. Begin the
business-site migration in its own source repository, behind an off-by-default release
gate. Do not replace a working production route merely because the new component exists.

This is a workload-fit choice, **not a measured universal performance winner or a completed
portfolio standardization**. SvelteKit combines shared components and routing with native
server-rendered forms and route-level prerender/SSR/client-rendering controls. Two current
portfolio sites already use it. Those facts support an incremental direction; they do not
prove lower maintenance cost or better user experience by themselves.

The spike remains open. Representative customer-scoped authentication/authorization
integration and constrained-device load/interaction measurements have not been completed.
Those missing comparisons must be recorded before the final acceptance of this decision
and before any claims depending on them. No weighted aggregate score is fabricated from
unknown inputs. Revisit the choice if an eligible alternative demonstrates a material
advantage against the frozen requirements, or the integrated application misses a floor.

Use these rendering patterns:

- Prerender public reading pages where practical. Do not hydrate a page that needs no
  application interaction; a small appearance controller is not application hydration.
- Render private customer/operator pages on the server, with explicit cache and origin
  boundaries. Never prerender customer data or share a customer-specific response.
- Prefer native links and forms; add client interactivity only for a demonstrated user
  benefit, then measure its bytes, accessibility and failure behavior.
- Keep the existing Go/PostgreSQL service authoritative for identity, invitations, roles,
  agreements, payments and the portal-owned work queue. Use the federated OIDC broker,
  not a collection of direct sign-in provider implementations. A Svelte frontend is not
  authorization and must not become a second payment/work authority.

## Evidence and alternatives

The retained [business-site comparison](https://github.com/devantler-tech/business-site/tree/18029834054e8951b134570463a6c13116b45f22/research/frontend-4019)
contains equivalent Astro and SvelteKit public pages and native forms, fixed fictional
data, lockfiles, production probes, build measurements and explicit limitations. Its
source is proposed in [business-site #133](https://github.com/devantler-tech/business-site/pull/133).
It is a bounded sample, not the private portal, real-provider acceptance or a full-product
benchmark. The link pins the evaluated source; adoption must rebind the final reviewed revision.

Both eligible samples delivered public/form HTML without application scripts or script
preloads and passed native HTTP form and foreign-origin controls. The final three clean
builds were Astro 1.97/1.31/1.24 seconds and SvelteKit 2.32/1.96/2.05 seconds on a shared Mac,
with Node 24.19.0 and npm 11.19.1. Caches and host load were uncontrolled. The retained
earlier batch differs substantially; neither batch supports a speed ranking. SvelteKit
also emitted unused browser bundles even with client rendering disabled: generated bytes
are not the same measurement as bytes referenced or transferred by a visited page.

| Option | Workload assessment and reason for the direction |
| --- | --- |
| Astro, including possible Svelte islands | Strong content-first baseline. The matched Astro sample also needs no browser application JS and supports native server forms. Astro plus Svelte islands remains credible, but its full integrated portal was not benchmarked here. Prefer one component/routing model for the evolving public/application UI, subject to the missing integrated evidence. |
| SvelteKit | Best-supported current direction for shared public/application components, native forms and selective rendering. Real About pages in EN/DA and the matched sample work; authentication and constrained-device comparisons remain open. Compilation and no virtual DOM are mechanisms, not user-experience measurements. |
| SolidStart | The evaluated 2.0.6 dependency graph failed the dependency-security floor through the currently unpatched braces advisory. Exclude that graph, not all future Solid versions. Preliminary scaffold parity defects are not framework defects or a fair ranking. Its documented Nitro 3 beta integration also needs an explicit operational fit assessment. |
| Qwik City | Resumability addresses client startup differently and deserves reconsideration if measured interaction/startup needs justify it. No equivalent local workload measurement was completed; do not claim Svelte outperforms it. |
| Next.js / Nuxt | Both offer server rendering and selective interactivity; neither is accurately described as necessarily browser-heavy. No demonstrated material advantage for this portfolio justified expanding this timeboxed implementation shortlist. Their exclusion is not a performance verdict. |

## Ownership, exceptions and consequences

Website and portal implementation, dependencies, deployment and product checks remain in
`devantler-tech/business-site`. This monorepo owns the portfolio architecture/adoption
record, not a second application or website publisher. ADR 0007 is unchanged.

The first source increment builds bilingual About pages from the same published business
copy and local assets. The production Astro publisher and Go service stay unchanged.
Subsequent migration needs full URL/content parity, user-path/a11y checks, actual source-owned
publication evidence and rollback proof. It is not safe to infer those from a sample or a
green build. Do not enroll in paid hosting or identity services through this decision.

Do not rewrite a healthy specialized interface for uniformity alone. KSail's embedded
cluster UI, the Data Product Controller's Go-rendered UI and World at Ruin's native Godot
game require their own workload evidence or a narrow recorded exception. Existing Svelte
sites still need conformance evaluation; using the same package does not establish equal
quality. Do not extract a shared component library without two real consumers.

The [frontend adoption guide](../frontend-standard.md) records the dated inventory, actual
linked follow-ups and cutover/exit criteria. Reversal is a reviewed decision followed by
removal of the isolated candidate; before a live route moves, retain and test its original
build/publication path. The temporary dual frontend has an owned retirement issue, not an
indefinite second website.
