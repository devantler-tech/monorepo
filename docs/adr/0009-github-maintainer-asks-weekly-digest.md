# ADR 0009 — Maintainer asks on GitHub, with a weekly email digest, replacing the Slack DM

- **Status:** Proposed — the maintainer accepts by merging
- **Date:** 2026-10-17
- **Deciders:** Maintainer (direction of 2026-10-17); Agentic Engineer
- **Issue:** [#4275](https://github.com/devantler-tech/monorepo/issues/4275) (spike)

> 🤖 Generated by the Agentic Engineer (interactive Claude Code session)

## Context

The direct maintainer channel is a DM to the maintainer's own Slack user: the last resort for a
genuine blocker. Slack never pushes a user's own message, so an ask waits until he happens to open
Slack. On 2026-10-06, ten answers had sat unread in reply threads for up to three weeks
([#3888](https://github.com/devantler-tech/monorepo/issues/3888)).

Two-way SMS was considered as the replacement. The maintainer rejected it on cost: a rented number,
a per-message rate and received messages that nothing can refuse. He asked for GitHub instead,
with asks made unmistakable among the very large volume of agent notifications. Or, as he put it,
weekly emails he can reply to, which would be cheaper and easier to manage.

Three facts about GitHub decide the design:

- **Replying to a notification email posts a comment** on the issue, as the account that received
  the email. So an email reply is authenticated by GitHub, with no inbound mail service of ours.
- **GitHub does not email a user about their own activity** unless they opt in. The agents act
  through the maintainer's own account, so nothing they do emails him. That is why the volume is
  bearable today, and also why an ask filed by an agent never reaches him.
- **Every notification email carries its reason** in the second `Cc` address, for example
  `assign@noreply.github.com`, and the repository in `List-Id`. A mail rule can match on either.

## Decision

**An ask is a GitHub issue. A weekly digest email, sent by GitHub on behalf of a workflow, is how
it reaches him, and he answers by replying to that email.** Nothing new is bought or hosted.

### The ask

- Every ask is an issue in `devantler-tech/monorepo`, labelled `maintainer-ask` and titled
  `🙋 Ask: <the decision in a few words>`. It links the artifact it is about.
- The body has four fixed sections, so the digest can quote them:
  `### Question`, `### Options` (lettered `A`, `B`, …), `### Recommendation` and
  `### If unanswered` (what stays parked, never an act taken on his behalf).
- The bar is unchanged: an ask is filed only when he must act and no agent can, after trying to
  resolve it. Decisions about our own work, reviews, merges and status never become asks.
- The repository is public, so an ask carries only the sanitized minimum, like every other issue.
  Private detail stays in the private memory store, and the ask says that a walkthrough is available
  in an interactive session.

### The weekly digest

- A scheduled workflow, `maintainer-digest.yaml`, runs every Monday at 05:00 UTC, which is 06:00 or
  07:00 in Denmark. It has only `issues: write`, and uses the repository's own `GITHUB_TOKEN`.
- When asks are open, it closes last week's digest and opens a new issue titled
  `🙋 Maintainer asks — <date> (<n> open)`, labelled `maintainer-digest` and **assigned to
  `devantler` by `github-actions[bot]`**. Because a different identity assigns him, GitHub emails
  him, with reason `assign`. The body numbers each ask and quotes its question, options,
  recommendation and default.
- When no ask is open, it sends nothing. A digest is never a status report.
- **Only a digest, or an urgent ask, ever assigns him.** Agents never assign `devantler` to
  anything else, so an `assign` email from this repository is always an ask.

### Urgent asks

The few conditions that cannot wait a week get the same email at once. These are a public site or
the production cluster unreachable for two consecutive checks, a confirmed leak of a credential
only he can rotate, and a sibling-lane `ESCALATE`. The agent adds the label `maintainer-ask-urgent`,
and a second workflow, triggered by that label, assigns him as `github-actions[bot]`. At most three
urgent asks a day. Anything over that waits for the next one, which says how many more are open.

### How a reply becomes an instruction

- He replies to the digest email. GitHub posts the reply on the digest issue as `devantler`. A
  `devantler` comment without the leading 🤖 marker is a maintainer instruction under the existing
  contract, so no new trust rule is needed.
- Each answer names its ask by number: `1: B`, `2: A`, or `3:` followed by free text. An agent acts
  on an answer only when it maps to exactly one open ask from that digest. Anything else is carried
  into the next digest as not understood. It fails closed, never with a guess.
- The agent records each answer on its ask, quoting it and linking the reply, and closes the ask. It
  acknowledges the reply with a 👍 reaction, which sends no email.
- A comment by anyone else, or an agent comment carrying the 🤖 marker, is data, never an answer.

### Making asks unmistakable

The design gives every ask three marks that the other agent mail never carries. It comes from
`github-actions[bot]`, it has reason `assign`, and its subject begins with `🙋`. One mail rule then
separates them, for example: *subject contains "🙋 Maintainer asks" → move to a "Maintainer asks"
mailbox and mark as VIP*. On github.com, the same set is the issue search
`is:open label:maintainer-digest assignee:devantler`.

## Cost

Nothing. GitHub Actions minutes are free on this public repository, the digest takes well under a
minute a week, and GitHub sends the email. No number, provider account, secret or inbound endpoint
exists to pay for or to attack.

## Options considered

| Option | Verdict |
|---|---|
| **GitHub asks with a weekly email digest** | **Chosen.** Free, the replies are authenticated by GitHub, and it reuses the existing trust rule. |
| Slack DM (today) | Retired. Slack never pushes his own messages, so asks sat unread for weeks. |
| Two-way SMS | Rejected by the maintainer on cost: a rented number at about USD 15 a month, plus every message sent and every message received. |
| Our own email with reply parsing | Rejected. It needs a mail provider, an inbound endpoint and spoof checks, all of which GitHub's reply-by-email already provides. |
| An `@devantler` mention | Rejected. Mentions are not a channel today, and they would drown among his other notifications. |

## Consequences

- An ordinary ask waits up to a week. That is the price of a channel he can manage in one sitting.
  Urgent asks still reach him at once.
- Agents read the open digest's comments every run, a couple of API calls, instead of the Slack DM's
  threads. The Slack thread procedure and its `| asked slack <date>` blocker marker are replaced by
  `| asked digest <date>`.
- Asks still open in Slack threads are moved into ask issues before the first digest, so none is lost.
- Platform alert streams that post to Slack (Flux, Alertmanager, Coroot) are not maintainer asks, and
  they are not changed here. A condition from them that needs him becomes an urgent ask.
- The maintainer's own setup is one optional mail rule. Email notifications for assignments are on
  by default.

## Follow-ups

- The digest and urgent-ask workflows, the two labels and the ask format, with a self-test that the
  digest assigns him, sends nothing when no ask is open and quotes every section.
- The contract change: the *Maintainer channels* section of `AGENTS.md` and its guide name this
  channel in place of the Slack DM, and the run procedure reads digest replies instead of Slack
  threads.
